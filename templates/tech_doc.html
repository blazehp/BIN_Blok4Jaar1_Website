SHROOMDB DOCUMENTATION

Last Updated: June 8, 2026

This documentation covers the whole ShroomDB codebase — every route, every function, what they're used for, how they work and how the pieces fit together. ShroomDB is a Quart ( async Python ) website that maps the microflora of mushroom compost: it takes raw nucleotide sequences, runs them through NCBI BLAST, retrieves the hits with protein and taxonomy data, stores everything in a MySQL database, and serves it through a searchable web interface.

This is an Interactive documentation. The contents on the left and the links throughout jump you straight to the section you need.

OverviewMental model ( the pipeline )

input → raw_blast → filtered_blast → protein / organism
  1. Input → BLAST.fill_db() reads an Excel file which contains a segment (100 forward + 100 reverse) of the sequences found in the compost and writes each sequence into the input table ( with an empty run_id ).
  2. BLAST → every not-yet-blasted sequence is submitted to NCBI with blastx, and every hit it returns is stored in raw_blast.
  3. Filter → filtering.filter_raw() keeps only the confident hits and copies them into filtered_blast. *This is the table the website actually serves.
  4. Retrieval → seek_protein() and seek_tax() take the distinct proteins and organisms out of filtered_blast and look up their function ( UniProt ) and taxonomy ( NCBI ), filling the protein and organism tables.
  5. Serve → the Quart routes read filtered_blast and render the tables, the detail pages and the analysis chart.

The neat part is the separation: the web layer only ever reads the finished tables. All the slow, network-heavy work ( BLAST, UniProt, NCBI ) runs separately in the pipeline files.

Web layerMain ( app.py )

The app.py file is where the server starts and where all the routes live. It's also where the filter form and the database table creation are defined.

On startup, it loads the .env, reads the PORT ( fallback 3000 ), builds the Quart app, and wires up CSRF protection using the CSRF_SECRET_KEY. It also forces Matplotlib onto the headless Agg backend — this is what lets the server draw charts without a display attached.

When you run app.py directly ( python3 app.py ), the if __name__ == '__main__' block runs all the CREATE TABLE IF NOT EXISTS statements for the five tables first, then starts the server. Debug mode is only turned on when PORT == "3000".

A few helpers live here too:

  • BlastFilterForm → a WTForms form describing the filter controls on the 200-sequence page. search_word is free text; organism is a dropdown filled in at request time; min_identity / min_score / min_bits are optional numbers; max_evalue is deliberately a string field so scientific notation like 1e-10 survives. sort_by and sort_order control the ordering.
  • blast_querying() → grabs every input row whose run_id is still NULL ( aka not blasted yet ), runs BLAST.query() on each, and sleeps 20 seconds between calls to stay under NCBI's rate limit.
  • delete_table() → drops tables in dependency order. *DANGER: only for a full wipe.

Web layerRoutes

Below are all the routes the app exposes. Same idea as a normal API — each one renders a page or kicks off a job.

[GET] /

The index route. Renders the landing page ( index.html ).

[GET] /blast

The picker page. Lets you choose between the 200 Sequences view and the Self BLAST view.

[GET] /200seq_blast

The workhorse route. This is the searchable results table, and it's worth explaining in full because it does a lot:

  1. It fetches all rows from filtered_blast in a single query.
  2. It builds the organism dropdown from the distinct organism names in those rows.
  3. It reads each filter from the query string, coerces the numbers with to_float(), and copies them back onto the form ( so the inputs stay filled in after you hit submit ).
  4. It filters the rows in Python using a local keep() function — text search across protein / organism / description, plus the numeric thresholds and an e-value ceiling — then sorts by the chosen column.
  5. It caps the list at 50 rows when no filter is active, and shows everything once any filter is set.

*Why filter in Python instead of SQL? Because fetching once and filtering in memory means no user input ever touches a SQL string ( no injection ), and the e-value math stays correct since e-values are stored as text.

[GET] /200seq_blast/<int:row_id>

Same handler as above, but with a row_id. This branch renders the single-hit detail page: it finds the row, gathers every hit in the same run, computes the stat cards and chart data via build_row_stats(), renders the three charts with render_row_charts(), and hands it all to the detail template.

[GET] /self-blast

The Self BLAST page. Currently a stub ( the template is there, the logic isn't yet ).

[GET] /analysis

Calls species_graph() to ( re )generate the taxonomic sunburst SVG, then renders analysis.html, which just <img>-tags the saved file.

[GET] /docs

This page.

[GET] /admin

The table browser. Reads a ?table= query param, checks it against a hard-coded whitelist of the five table names, selects everything from that table, then converts the raw tuples into a list of dicts ( column name → value ) so the template can address cells by name. *That whitelist is the thing keeping the f-string query safe.

[GET] /run_blast

Triggers a BLAST run. Because blast_querying() is slow and blocking, this route offloads it to a thread with run_in_executor() and immediately returns "Blasting..." so the request doesn't hang.

[GET] /_creds

Returns the database credentials as JSON. This is a localhost-only route and a security risk — see Known Issues.

Data layerdatabase_config.py

This file centralises the MySQL connection so the rest of the codebase never has to think about it.

It reads every connection setting from environment variables ( DB_USER, DB_PASSWORD, DB_HOST, DB_PORT, DB_DATABASE and the pool settings ), so no credentials live in the source code.

  • class DB → wraps the connector. Its connect() method returns the existing live connection if one is already open, otherwise it opens a new pooled one.
  • db → at the bottom of the file, db = DB().connect() creates one shared connection. Every other file imports it with from database_config import db. Think of it as the single doorway into the database.

Data layerdatabase_manager.py

This is the one place that knows how to safely read and write the database. Everything else goes through it.

The base class is _DatabaseManager, and there's one subclass per table that pre-loads the right columns. You always use it the same way: make an instance with a cursor, fill its .column[...] dict, then call a method.

_DatabaseManager methods

  • select(columns="all") → runs SELECT * ( or specific columns ) and returns all rows.
  • insert() → inserts the current data dict using placeholders ( %s + a value tuple ). Injection-safe and allows None values. *It warns you if any value is None.
  • update(position, pvalue) → runs one UPDATE per non-None column, matching on position = pvalue.
  • delete(record_id) → deletes the row with that id.
  • custom_query(query, returns, params) → the escape hatch for raw SQL. Pass params to use safe placeholders, and returns=True when you expect data back.

The table subclasses — InputTable, RawBlastTable, FilteredBlast, ProteinTable, OrganismTable — each just define their column dict and hand it to the base class.

Two things to watch. update() and delete() build their SQL by string interpolation ( not placeholders ), so they're not injection-safe — only call them with trusted values. And OrganismTable defines a "sex" key where it almost certainly means "genus", which clashes with what seek_tax() writes later.

The pipelineparsing.py

A tiny file with one job: read the course Excel file.

  • parse_excel(file_path, sheet_name) → reads the spreadsheet with no header row and slices it into two two-column frames ( columns 0–1 and columns 3–5 ), returned as a tuple. The dataset stores two sequence reads side by side, so this splits them — BLAST.fill_db() later recombines and de-duplicates the sequence column from both halves.

The pipelineBLAST.py

This is where sequences actually get sent to NCBI and the results get parsed into the database.

  • query(sequence, seq_id) → the core BLAST call. It submits one sequence with NCBIWWW.qblast(program="blastx", database="nr", ...), parses the returned XML, and reads the first record. The record's query_id is written back onto the matching input row ( aka marking it as blasted ). Then it loops twice:
    • For each alignment ( a hit ), a regular expression pulls the accession code, description and organism out of the hit title.
    • For each HSP inside that alignment, it records the e-value, bit-score, raw identity count, score and a coverage percentage ( align_length / query_length × 100 ), derives a clean protein name by stripping the organism out of the description, and inserts a row into raw_blast.
  • fill_db(path) → parses the Excel file, concatenates the sequence column from both reads, drops the blanks, and awaits push_to_db() for each one.
  • push_to_db(sequence) → inserts a single sequence into the input table.

*Heads up: the identity_perc column is filled from hsp.identities, which is the raw count of identical residues — not a percentage. Worth converting if you want a true %.

The pipelinefiltering.py

This file turns the messy raw_blast table into the clean filtered_blast table, then retrieves the protein and taxonomy data.

  • evaluate(e_value, bit_score, score, identity) → the confidence gate. Returns True only if a hit clears every threshold ( bit-score, score and identity each ≥ 50 ) and passes the e-value test. *See the warning below — the e-value check looks inverted.
  • filter_raw() → reads every row from raw_blast, skips the ones whose run_id is '-', runs each survivor through evaluate(), and inserts the passing ones into filtered_blast.
  • seek_protein() → reads the distinct proteins out of filtered_blast and builds the protein table. For a protein it hasn't seen before, it looks up the function with get_protein_function() and inserts a new row; for one it has seen, it appends the new hit id to that protein's comma-separated hit_id list. A 0.33s sleep between new entries keeps it under the UniProt rate limit.
  • get_protein_function(protein_name) → hits the UniProt REST API: searches for the protein, takes the top accession, fetches that entry's cc_function annotation, and returns the FUNCTION text. Every failure mode ( no result, HTTP error, connection error, timeout ) returns a descriptive sentinel string instead of crashing, so the caller always gets something it can store.
  • seek_tax() → the taxonomy twin of seek_protein(). Walks the distinct organisms in filtered_blast and fills the organism table with family / genus / species, de-duplicating by appending hit ids.
  • get_taxonomy(acc_code) → calls NCBI Entrez ( efetch against the taxonomy database ), reads the record, and walks its lineage to pull out the genus and family ranks.
⚠ Likely inverted e-value filter. evaluate() does if e_value < 1e-30: return False, which rejects the most significant hits — smaller e-values mean better matches. This almost certainly should reject hits whose e-value is too large. Double-check before trusting the filtered set.
⚠ Import-time side effects. The module ends with a bare seek_tax() call, so simply importing filtering kicks off a full taxonomy run. It also imports a name from retrieve_protein.py, which runs its own network code on import. Both should be guarded behind if __name__ == "__main__":. Also note get_taxonomy() is handed an accession code where Entrez taxonomy expects a numeric taxon id.

The pipelineretrieve_protein.py

A small scratchpad / reference script for the UniProt API.

It demonstrates Biopython's Bio.UniProt.search against a sample query ( reviewed SARS-CoV-2 proteins ) and prints accessions and organism names. It reads more like a proof-of-concept than part of the live pipeline.

*Because filtering.py imports a name from this file, its top-level code runs on import. Wrapping the demo in a main guard avoids surprise network calls.

Visualisationhelper.py

Everything the single-hit detail page needs — the stats and the charts. Matplotlib is pinned to the Agg backend here too.

  • to_float(value) → safe float conversion. Returns None instead of crashing on bad input. Used all over the filtering code.
  • build_row_stats(row, run_rows) → given one hit and all the hits in its run, it computes the stat cards ( the row's rank by score, the run totals, the average score / bits / identity ) and assembles a chart_data payload ( identity, a this-hit-vs-run-average comparison, and the top-10 hits by score with the current hit flagged ). *It tolerates the coverage / converage spelling difference by checking both.
  • make_chart(fig) → renders a Matplotlib figure to a transparent PNG, base64-encodes it, and returns a data: URI. This is the trick that lets the templates drop charts straight into <img src> with no files written to disk.
  • render_row_charts(chart_data) → produces the three charts: an identity pie, a grouped bar chart of this hit vs the run average, and a horizontal bar chart of the top hits by score with the current one highlighted. The colors are mirrored from blast.css.

Visualisationvisualisation.py

The chart-drawing toolkit — pie charts and the taxonomic sunburst.

  • create_piechart(values, title) → plots a labelled pie chart from a { label: value } dict and saves it as an SVG under graphs/.
  • create_sunburst_chart(nodes, title, ...) → a recursive radial renderer that draws a hierarchical taxonomy as a sunburst. Each node is a ( label, value, subnodes ) tuple. Think of it like drawing rings from the inside out: the function descends level by level, draws one ring of bars per level with each wedge's width proportional to its value, and recurses into the children. At the root it flips the polar axis to read clockwise from the top, hides the axes, and saves the result as an SVG under static/.

Visualisationanalysis.py

The bridge between the pipeline and the /analysis page.

  • species_graph() → right now it's a placeholder: it builds a hard-coded taxonomy tree and hands it to create_sunburst_chart(), saving the SVG the analysis page displays. The commented-out lines show the intended direction — querying the real tables to build the tree from actual data.
⚠ Filename casing. species_graph() saves with the title "Speciestest" ( capital S ), but analysis.html requests speciestest.svg ( lowercase ). On a case-sensitive filesystem ( Linux ) the image won't load until the casing matches.

ReferenceDatabase schema

Five tables, all created in app.py's __main__ block.

Table Key columns Role
input id, sequence, run_id ( unique ) Raw ingested sequences; run_id gets filled once blasted
raw_blast run_id ( FK→input ), accession_code, e_value, score, bits, identity_perc, converage Every hit / HSP from BLAST, unfiltered
filtered_blast same shape as raw_blast The confident hits only — what the website serves
protein protein_name, protein_function, hit_id Distinct proteins + UniProt function; hit_id is a CSV of source rows
organism organism_name, family, species, hit_id Distinct organisms + NCBI taxonomy

*The coverage column is spelled converage in the schema; build_row_stats() already handles both spellings, but it's worth fixing at the source. The organism table is also created with a sex column and no genus column, which conflicts with what seek_tax() writes.

ReferenceKnown issues & security

Collected here so they're easy to find. None of these break the demo, but they're all worth fixing before the project is graded or put anywhere public.

  1. /_creds exposes secrets. This route hands the DB username, password and CSRF secret to anyone who asks. Remove it or lock it strictly behind debug-only access. *This is the urgent one.
  2. Inverted e-value filter. evaluate() currently rejects the strongest hits ( see filtering.py ). Check the comparison direction.
  3. Import-time side effects. filtering.py runs seek_tax() on import, and importing it drags in retrieve_protein.py which also hits the network. Guard both with a __main__ check.
  4. String-built SQL in update() / delete(). These are injection-prone; use the safe placeholder pattern from insert() / custom_query() everywhere.
  5. Missing admin CRUD routes. The admin template's Add / Edit / Delete buttons point at routes that don't exist in app.py yet.
  6. PORT type mismatch. It's set to the integer 3000 on startup but compared against the string "3000" later, so the two never match. Normalise it to one type.
  7. Schema mismatches. The converage typo, the sex-vs-genus organism column, and the Speciestest.svg casing all need reconciling.
